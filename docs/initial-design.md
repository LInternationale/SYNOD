# SYNOD 初始设计蓝图

当前实现按本机标签划分子工作区. 标签位于队伍对应的本机状态目录，旧版名册中的空间作为初始标签. 新建队伍在引导结束后从偏好配置标签. 工作目录保持普通文件夹结构，按相对路径对应队伍仓库中的共享文件. 设备的默认检查间隔为 30 秒，可在偏好调整. [同步设计与验证](implementation.md#session-driven-synchronization)


当前队伍 Git 协议为 v2. 操作信息写进 commit message，文件版本由 Git 保存. 下文涉及事件文件的约定仅用于读取 v1 仓库. 正文待办和子任务按当前进度规则汇总. [当前 Git 协议](git-commit-format.md) · [进度规则](implementation.md#inline-checklist-revision-and-independent-review)

## 一场比赛里的六个成员

以下示例使用三位队员和三位 AI 助手。队伍名册可持续添加成员。每个成员有自己的地址，可以给人或助手寄信。每台客户端最多激活一位人类和一位 AI。可均不激活，或只激活人类。激活 AI 需要同时激活人类。人使用 Rust + Ratatui 的终端界面，助手在宿主已有的会话中通过 MCP 办事。客户端在后台同步队伍数据，查信由正在运行的助手主动发起。

**队伍公告板**展示本队全部已寄出的信件。每位队员和 AI 助手同步后，都可以打开同一封信，查看正文、附件、依赖、进度及已记录的事件。收件人和抄送用来筛选信件、提醒相关成员。**共享工作区**保存多人编辑的实际成果，例如模型代码和论文。GitHub 托管每支队伍自己的数据仓库，本项目仓库用于开发 SYNOD 程序。两类仓库的可见性可分别选择。

## 一封信如何从草稿走到完成

| 用户动作 | 客户端的工作 | 用户能确认的结果 |
| --- | --- | --- |
| 写信 | 分配稳定的信件编号，在隔离的工作副本中从已知主线建立专属草稿分支 | 编辑器打开，可以填收件人和抄送、写正文和添加附件 |
| 存草稿 | 保存本机快照并推送到远端草稿分支 | 远端确认后显示「草稿已存至云端」，同一身份换设备可续写 |
| 寄信 | 固定此刻编辑器中的版本，保存草稿，将原件和寄出事件一起发布到远端 `main` | 确认后显示「已寄出」。全队下次同步时可见，收件人与抄送成员获得定向提醒 |
| 勾选「任务完成」 | 当前身份对原信提交一个 `MarkedCompleted` 事件 | 完成者看到勾选及同步状态，其他客户端同步后在同一封信上看到同一个勾 |
| 查看进度和依赖 | 从原信的事件计算百分比、完成状态，以及尚在等待的前置信件 | 每位成员都可以查看哪些事正在等这封信、哪些事已经可以开始 |

Alice 勾选《重画图 3》只需一次操作。UI 和 MCP 都调用同一个「标记完成」用例，后台自动发布。发件人收到的状态更新留在原信上。以后加入历史界面时，可以直接显示「Alice 于 15:42 将任务标记为已完成」。第一版从第一次寄信起就保存所需的身份和时间。

公告板默认打开「全部信件」。切到「发给我的」按当前身份匹配收件人，切到「抄送我的」则匹配抄送名单。直接按编号打开一封已寄信时，读取范围始终是当前队伍的公告板。客户端按队伍、身份和寄出事件编号记录本机已提示的新信。一个成员即使同时列在两处，或客户端重复同步，也只收到一次定向提醒。助手在已有会话主动查信时读取提醒。

## 数据目录与事件

每封信有自己的目录，共享工作区与信件并列存放。源码模块、队伍仓库、本机状态、用户工作目录和验收样例的具体路径以[文件组织规范](file-layout.md)为准。

| 对象 | 数据契约 |
| --- | --- |
| 队伍 | `team.json` 记录格式版本、成员编号与类型、显示名、子工作区编号与名称。GitHub 凭据交给本机凭据机制。 |
| 信件原件 | `envelope.json` 含信件编号、发件人、收件人 `to`、抄送名单 `cc`、标题、初始依赖的信件编号，以及附件编号与原文件名的对应关系。`to` 与 `cc` 使用队伍成员编号，缺省的 `cc` 按空名单读取。回复关系记录在独立的 `references` 数组，缺省为空；一封信可引用多封已寄信。前置依赖单独保存在 `initial_dependencies`，用于任务等待关系。正文采用 Markdown。寄出时封存元数据、正文和附件。 |
| 事件 | 每次动作有独立编号、目标信件、操作者、操作时间、事件类别和相应载荷。已发布事件只追加。寄出、报告进度、标记完成以及增减依赖均有明确类别。 |
| 本机状态 | 两个身份位、草稿编辑现场、待投递操作、子目录策略与同步基线在团队工作目录之外持久化。公告板、全队标题索引、任务图与当前进度可以从已发布记录重建。 |

一条完成事件可以保存成下面的 JSON。编号采用便于阅读的示例值，时间带有时区。

```json
{
  "schema_version": 1,
  "event_id": "evt-018",
  "letter_id": "letter-042",
  "actor_id": "member-alice",
  "occurred_at": "2026-11-26T15:42:00+08:00",
  "kind": "MarkedCompleted"
}
```

主线每次发布至多接受一个信件动作，寄信时原件和 `LetterSent` 属于同一次发布。只改工作区的提交可以没有信件事件。所有客户端沿 `main` 的第一父提交链，按每次发布相对于前一主线版本新增的事件重放。草稿的中间提交留在草稿历史里。操作时间供人阅读，主线接纳顺序决定共同状态，离线设备时钟快慢也能得出相同的复选框值。

初始状态为待办，进度为 0%。1% 至 99% 表示进行中，填写 100% 与勾选完成走同一动作。完成后到达的旧进度上报显示「这封信已经完成」。寄出时校验信封中选定的前置信件，用它们建立初始依赖，之后按增减依赖的事件更新。若未开工的 B 依赖 A，B 显示「等待 A」，其所有前置信件完成后，B 显示「可开始」。

## 消息系统的不变量

以下保证适用于经 SYNOD 写入消息目录的客户端。普通工作区操作的写入范围限定在所选 `workspace/<space-id>/`。公告板收录远端 `main` 上已寄出的信。云草稿仍保存在各自的草稿分支，队伍仓库的读取权限也覆盖这些分支及附件。

1. **各封信的写入互相独立。** 草稿分支只允许变更本信的信封、正文与附件。寄出后，原件固定，后续操作各自新增一个事件文件。公告板从已寄信和事件生成，六个成员可以同时寄信。
2. **一个动作有一个可重试的身份。** 本机先持久化操作编号、目标和内容，再尝试网络发布。重试使用原编号。远端已有完全相同的动作即确认成功。同一编号的内容不同则保留本机输入，报告记录不一致。对同一份已寄出的原件再次按「寄信」直接返回寄出结果，若送来另一版本，则将其保留为草稿。
3. **主线按顺序接纳经过校验的动作。** 读取最新 `main`，先查幂等结果，再检查重名、身份、依赖和任务状态。以刚检查过的主线为第一父提交构造候选，核对候选相对主线只增加本次动作允许的文件，再使用普通快进推送。若其他客户端先发布，重新抓取、重验并重建候选。依赖引用须指向已寄出的信。两个人同时添加「A 等 B」和「B 等 A」时，后到的一笔可以解释为「这两封信会互相等待」。
4. **提交目标状态。** 勾选表达「标记为已完成」。同一事件重发只记一次。两个不同成员同时完成同一封信，先被接纳的事件保留署名，后到者看到「已经完成」。百分比上报随操作携带观察到的上一进度版本。若另一人刚改成不同值，显示其当前值并保留本次输入供确认。
5. **分清本机、云草稿与已寄出。** 离线时显示「已存于本机，等待同步」或「等待寄出」。草稿分支收到远端确认后才显示「草稿已存至云端」，远端主线包含该次发布后才显示「已寄出」。草稿引用放在 `drafts/<actor-id>/<letter-id>/<copy-id>` 下，换机时按当前身份枚举并抓取。续写以读到的草稿版本为基线。遇到并发保存时给后一个版本建立云端副本，副本编号与该保存动作绑定，重试可以找回同一份副本。

**一支队伍的所有已寄信件共享同一组标题。** 从最新远端 `main` 的全部已寄信件建立标题索引，按去掉首尾空白后的完整标题比较，已完成的信也在索引中。标题归属信件编号，收件人、抄送和当前界面筛选均不参与计算。草稿可以同名，各支队伍独立查重。两封同名信即使分别写给 Alice 和 Bob，也只有先发布的那封进入公告板。另一位发件人看到「队伍公告板已有一封《重画图 3》，草稿已保留」，可以直接打开已有信件。

同一客户端的两个入口连接唯一的会话宿主。宿主按队伍串行处理发布，保存操作编号和冻结输入，使用隔离的 Git 工作副本执行尝试。短暂的本地事务负责记录状态，网络请求在事务外进行。进程重启时先按编号核对远端，再决定重试或确认。如遇无法识别的格式版本或事件，保留最后一次可验证的视图，提示更新客户端后继续同步。[共享会话的生命周期和竞争处理](client-session.md)

## 子工作区如何独立同步

每个子工作区拥有独立的本机可编辑目录、上一次成功应用的远端目录版本，以及本机同步偏好。客户端定期抓取远端 `main` 到本地缓存。消息视图随之刷新，用户正在编辑的文件则按对应子目录的策略更新。[Git 抓取语义](https://git-scm.com/docs/git-fetch)

| 策略 | 发现该目录有新版时 | 用户能做什么 |
| --- | --- | --- |
| 仅手动 | 显示「有更新」，保留当前工作现场 | 选择「获取更新」时预览并应用 |
| 无修改时自动同步 | 比较当前目录与自己的基线。没有本机改动才应用新版，有改动则提示「有更新，本地有修改」 | 先发布自己的工作，或手动比较双方版本 |

本地改动包括新增文件、删除、重命名和内容修改，也包括尚待发布的工作。对每个子目录分别判断。即使远端同一次提交同时修改 `code` 和 `paper`，本地正在修改 `code` 的队员也能先收到干净的 `paper` 更新。

实现时按子树读取和发布。对外提供普通目录，对内保存该目录的基线、目标版本和待应用清单。更新时暂存新内容和可恢复的原件，逐项复核本机路径与预期内容。有新编辑就保留两份供比较，全部应用成功后才推进该目录的基线。中断后凭清单继续或还原。手动同步时比对基线、本机和远端三个版本，同一路径有不同编辑就列出具体文件供选择。发布只带所选子目录的变动，并基于最新主线重验。消息发布使用隔离的 Git 工作副本，写信时用户的代码和论文继续保有各自的编辑现场。[Git 工作副本](https://git-scm.com/docs/git-worktree)

## Rust 组件与接口

首版采用一个 Cargo 包，包含库和二进制组合入口。模块职责如下，文件归属以[源码目录约定](file-layout.md)为准。

| 模块 | 职责与依赖 |
| --- | --- |
| `mail` | 从全队已发布事件还原信件、标题索引、进度及依赖图，判断下一动作能否接纳。在公告板上按成员筛选信件并计算提醒对象。 |
| `workspace` | 子目录策略、基线比较与同步决策。输入目录差异，输出应用、等待或需比较的路径。 |
| `application` | 对会话绑定的操作者执行写信、保存、寄信、完成、查询及子目录同步用例。依赖两个领域模块，并拥有 `DraftStore`、`TeamHistory`、`WorkFiles` 和 `Outbox` 等所需接口。 |
| `session` | 独占同一客户端的应用实例、身份位、同步循环和写队列，向 TUI 和 MCP 提供同一份视图。 |
| `adapters::git`、`adapters::local` | Git 适配器集中执行 commit、checkout 及其他 Git 操作，为每次队伍提交写入完整 TOML 消息。文件适配器负责本机草稿、待投递数据、基线和文件更新恢复。两者实现应用层接口。 |
| `tui`、`mcp` | TUI 用 Ratatui 呈现信息，MCP 经标准输入输出提供工具。它们作为前端连接同一会话，分别绑定人类位与 AI 位。 |
| `main` | 分派 TUI、MCP 桥与会话宿主角色。会话宿主根据启动配置组装应用层和适配器。 |

领域接口采用 `LetterId`、`EventId`、`ActorId` 和 `SpaceId`。状态机用所有权表达草稿快照、待发布与已确认之间的转换。配置在启动时解析，文件和工具参数在入口处解析为合法编号、时间、百分比和相对路径。附件原名用于展示，存储位置由编号确定。文件适配器检查路径边界与符号链接，Git 参数通过参数数组传递。界面将连接失败、需要重新登录、过期编辑、重名和无效依赖分别映射为可操作的提示。

同一会话内的两个身份位分别绑定到队伍名册中的人和助手，由宿主根据连接身份署名。Git 凭据负责仓库访问。作者可续写自己的草稿。当前版本不设应用层权限系统。所有用户均可查看已寄信、登记进度、勾选完成及修改依赖。`to` 和 `cc` 仅供筛选与提醒。换账号后，排队中的动作保留创建时的署名，按原身份发布。

预期 MCP 查询包括 `list_letters` 和 `read_letter`。前者默认返回队伍公告板的全部信件，支持 `to_me` 和 `cc_me` 筛选。后者按信件编号读取同一队伍的已寄信。助手通过 `save_draft`、`send_letter`、`mark_completed` 和 `list_dependencies` 等用例办理任务。两种入口返回同一份信件视图与发布状态。MCP 只在助手主动调用时办理动作。[Ratatui](https://ratatui.rs/) · [MCP 架构](https://modelcontextprotocol.io/docs/learn/architecture)

## 验证计划

| 编号 | 验收场景 | 预期证据 |
| --- | --- | --- |
| A1 | 同一设备登录一个人和一个助手，分别发信，第二台设备同步 | 两封信各有正确署名，两个入口读取的同一封信内容一致 |
| A2 | 写信、云存草稿、换设备续写、寄信，另测两台设备并发续写 | 寄出前只在草稿分支，寄出后原件与事件一起出现于主线，分叉草稿两份均可恢复 |
| A3 | 两个客户端同时把同标题寄给不同成员，使用不同抄送和筛选，再试不同标题、已完成信的标题及丢失确认后重试 | 全队只接纳一封同名信，另一份仍在云草稿中。已完成信继续占用标题，异名都能发布，同一原件重试成功 |
| A4 | Alice 勾选后断线并重试，同时发件人也点击完成 | 主线上只有一个生效的完成事件，双方同步后看到同一复选框，历史可还原实际先完成人的身份及操作时间 |
| A5 | 并发添加反向依赖、并发报告不同进度 | 主线保持无环，过期进度提示指出他人已填的值 |
| A6 | 同一远端提交修改两个空间，本地一处干净，另一处有修改或新增文件 | 「仅手动」只提示，自动策略只更新干净目录，本机工作可恢复，两个基线独立 |
| A7 | Git 中断、拒绝写入或客户端在推送与记录结果之间退出 | 可以恢复、重试或重新登录，远端确认前 UI 保持待同步状态 |
| A8 | 越界附件路径、旧客户端遇到未知事件、投递时切换账号、子目录更新途中退出 | 输入在边界被处理，视图停在可验证版本，署名正确，本机文件可按清单恢复 |
| A9 | 寄给 Alice，抄送 Bob。用两种入口分别以收件人、抄送成员及未列名成员的身份读取，并重复同步 | 所有人在「全部信件」及按编号查询中都能查看同一原文、附件、状态和事件。两个个人筛选各自命中，只有 Alice 和 Bob 获得定向提醒，本机重复同步只提醒一次 |
| A10 | 从样例重放云草稿、寄信、完成与子工作区的 Git 历史，逐一读回提交对象 | 完整消息可解析为 TOML，父提交、字段及差异路径符合类型约定，主线文件与样例逐字节一致 |
| A11 | TUI 和 MCP 同时首次连接，同一封信同时完成，一端退出或宿主中断后重连 | 同机只有一个会话所有者和同步循环，合法写操作按序接纳，另一端可继续办理，恢复后按原编号确认 |

实现阶段用纯领域单元测试覆盖状态转换，再用临时裸 Git 仓库、可控时钟和两个独立客户端测试并发与故障恢复。公开 Rust 接口补文档测试，入口层以 Ratatui 的终端测试后端和 MCP 工具调用做交叉验收。Rust 代码落地后依次运行 `cargo test` 和 `cargo +nightly llvm-cov --branch`，检查修改文件的分支覆盖率。

## 独立设计评审与交付范围

复核草案时发现以下会影响实现的缺口，修订后的约定及对应验收如下。

| 评审发现 | 修订与检验位置 |
| --- | --- |
| 只抓取主线，换机后找不到已上传的草稿。并发保存的失败重试还可能产生许多副本 | 规定按身份发现草稿引用，用保存动作编号定位并发副本，见 A2、A7 |
